# Reviewer A: PR #93 Google Drive connector (`git diff 904c1d3 fcba1e8`)

## Findings

### 1. [warning] Sync deletes the old document before the checks that are certain to reject the new one
**Location**: plateform_back/src/connector/connector.service.ts:93-97; plateform_back/src/document/document.service.ts:80-101
**Finding**: `syncGoogleDrive` runs `documentService.delete(doc.id)` and then `ingestFile(...)`. The pre-delete `download()` only checks the MIME type and size from the metadata. Every other check in `ingestFile` runs after the old version is gone: empty buffer (l.80), `matchesDeclaredType` (l.85), dataset quota (l.89-94), and name uniqueness (l.99-101). When one of them throws, the document has left the dataset, and so has the agent's retrieval. The user only sees a line in `failed`, such as "Un document nommé « X » existe déjà". Nothing says the previous version was removed.
**Evidence**: The name collision can be reproduced on demand and is not an edge case. Import Drive file `Notes.pdf`, then upload a manual file `Rapport.pdf` (or import a second Drive file with that name). Rename the first Drive file to `Rapport.pdf` (renaming bumps `modifiedTime`) and click "Resynchroniser". Line 87 finds `modifiedTime` newer, l.93 downloads, l.96 deletes `Notes.pdf` from the engine, S3 and the DB, and l.97 → `findByName` throws `ConflictException`. `toFailure` turns that into a failure entry, and the document is gone. The same happens when a Drive file is emptied (0 bytes passes the `size` metadata check at l.111 and fails at document.service.ts:80). The code comment says "if the re-ingest fails… Replace in place if that happens in practice", which treats this as rare. These cases are deterministic. The `UPLOADED/PROCESSING` guard (l.81) also reads a snapshot taken at l.70, before a serial loop of Drive round trips and 15 MB downloads. A "retry" clicked during that window (retry does not check status, see audit #9) makes l.96 delete a document whose job is still running. That is exactly the case the guard says it prevents. No test covers any post-delete ingest failure. `connector.service.spec.ts` "should replace a document modified in Drive" only covers the happy path.
**Suggestion**: Pull the pure checks out of `ingestFile` into a `DocumentService.assertIngestable(datasetId, file, { replacing?: Document })`: empty, size, type and signature, quota as `used - replacing.size + file.size`, and name collision excluding `replacing.id`. Call it in sync before `delete`, and re-read the document's status right before deleting. Add a spec where the renamed file collides and assert that `delete` is not called.

### 2. [warning] Trashed Drive files are treated as live, and every 403 is reported as "supprimé"
**Location**: plateform_back/src/connector/google-drive.client.ts:5, 68-71; connector.service.ts:85-90, 117-125
**Finding**: `FILE_FIELDS` does not request `trashed`. Drive v3 `files.get` on a trashed file returns 200 with the full metadata, and `alt=media`/`export` keep working until the trash is emptied. Trashing does not change content, so sync reports the file as `unchanged` (l.87-89) and the agent keeps answering from a document the company deleted in Drive. Trash is the normal way to delete in Drive, so the "deleted Drive files handled" intent is only met for permanent deletion (404), and even then the document stays indexed and is reported as failed on every sync. Separately, `request()` maps every 403 to `DriveFileUnavailableError`. That includes `exportSizeLimitExceeded`: a Google Doc or Slides whose PDF export is over Google's 10 MB limit, which `download()` cannot pre-check because native files have no `size`. It also includes `rateLimitExceeded`/`userRateLimitExceeded`. The user is told the file was deleted or unshared and can never fix it. A 429 becomes "Erreur inattendue", and the loop keeps calling Drive for the remaining files.
**Evidence**: Path: sync l.85 `getFile` → 200 `{…}` with no `trashed` field read → l.87 `modifiedTime <= externalModifiedAt` → `unchanged++`. The client spec's "should stop on an expired token and report a missing file" only exercises 404. No test covers trashed or 403 reasons.
**Suggestion**: Add `trashed` to `FILE_FIELDS`. Treat `trashed: true` like 404 in both import and sync, and decide explicitly whether sync deletes or flags such documents. Parse `error.errors[0].reason` on 403 so `exportSizeLimitExceeded` and rate limits get their own messages (and rate limits stop the run like 401 does).

### 3. [warning] Downloads are bounded only by a separate metadata call, with no byte cap and no timeout
**Location**: plateform_back/src/connector/google-drive.client.ts:56, 66-68; connector.service.ts:111-114
**Finding**: The "no unbounded downloads" guarantee depends entirely on the `size` returned by an earlier `files.get`. `download()` then fetches `alt=media`, which always serves the current head revision, and buffers the whole body with `arrayBuffer()`. It never checks `Content-Length` or counts bytes. `fetch` gets no `AbortSignal`, so a stalled Drive response holds the HTTP request (and up to 19 more serial files) for undici's default 300 s headers and 300 s body timeouts.
**Evidence**: Between `getFile` (l.85 / l.48) and `download` (l.93 / l.55), a new revision of any size can be uploaded to the same file id. The whole body is held in memory before `ingestFile`'s size check (document.service.ts:81) rejects it. The window is short, so exploitation is unlikely. But the intent lists unbounded downloads explicitly, and the fix is local and cheap. The missing timeout is the more practical problem: the import endpoint already runs up to 20 sequential downloads inside a single request (acknowledged "shortcut" comment l.42).
**Suggestion**: Pass `signal: AbortSignal.timeout(60_000)`. Reject when `Content-Length > MAX_FILE_SIZE`, and read `response.body` as a stream with a running byte count that aborts past `MAX_FILE_SIZE`, so the limit holds whatever Drive serves.

### 4. [warning] Agent analytics now imports the whole runtime module to read dataset ids from a workflow
**Location**: plateform_back/src/agent-analytics/agent-analytics.module.ts:13; agent-analytics.service.ts:22-24, 49-51; agent-runtime/agent-runtime.builder.ts:55-75; agent-runtime.module.ts:37
**Finding**: To compute document health, `AgentAnalyticsModule` now imports `AgentRuntimeModule`, which brings the runtime controller, BullMQ usage queue/processor, credit module and stream forwarder. `RagPipelineBuilder` is exported just so analytics can call `resolveDatasetIds`. That method is not pipeline building. It is "workflow version → retrieve block → `DatasetService.resolveOrgIdsForAgent`", and it only depends on `AgentService`, `WorkflowService` and `DatasetService`. Putting it on the runtime builder couples a read-only dashboard query to the runtime's module graph, and the next consumer (workspace stats, the dataset "agents" tab) will import the runtime too.
**Evidence**: `resolveDatasetIds` uses none of the builder's runtime-specific logic (`applyInstructionOverride`, Zod pipeline validation, `orgIdOverride`). It only reuses `loadRawBlocks` and `datasetIdsOf`. The front then polls this endpoint every 5 s while documents index (`DocumentHealthCard.tsx`), and each poll runs `findProductionWorkflowVersion` plus a full workflow `definition` load plus `findDatasetIdsByAgent` plus the `groupBy`.
**Suggestion**: Move `loadRawBlocks`/`datasetIdsOf`/`resolveDatasetIds` into a small provider in `WorkflowModule` (or `DatasetModule`), for example `WorkflowDatasetResolver.resolveSearchedDatasetIds(agentId)`. `RagPipelineBuilder` and `AgentAnalyticsService` both inject it, and `AgentAnalyticsModule` drops the `AgentRuntimeModule` import and the extra export.

### 5. [nit] An expired token mid-run drops the partial result
**Location**: plateform_back/src/connector/connector.service.ts:119
**Finding**: `toFailure` rethrows `DriveAccessExpiredException` from inside the loop. Files already imported, or documents already replaced in sync, are committed, but the client only receives a 400 "Accès expiré" and the toast says the import failed. A re-run then reports the done files as "Déjà importé" under `failed`, which the front shows as an error toast when `imported === 0` (useGoogleDrive.ts:70).
**Suggestion**: Break out of the loop and return the partial result with a top-level `aborted: 'token_expired'` flag instead of throwing.

### 6. [nit] A duplicate `externalId` is reported as a duplicate name
**Location**: plateform_back/src/document/document.service.ts:116-121; prisma/schema/document.prisma `@@unique([datasetId, source, externalId])`
**Finding**: Two concurrent imports of the same Drive file pass the `alreadyImported` snapshot (connector.service.ts:35-39) and hit the externalId unique index. The P2002 handler only knows about names and answers "Un document nommé « X » existe déjà". Behaviour is safe, but the message is wrong. Check `error.meta.target` to return "Déjà importé".

### 7. [nit] The worker concurrency is pinned to a constant in the local engine copy
**Location**: plateform_back/src/document/document.processor.ts:11-12
**Finding**: The comment ties `concurrency: 5` to `rag-engine/app/main.py num_workers=5`, which is the local dev copy. The production engine is the external `RAGENGINE_URL` (and `RAG-GenRag/` with its own `worker/`). The value is also per backend instance, so N replicas send 5×N concurrent ingestions. Make it an env setting (`DOCUMENT_INDEXING_CONCURRENCY`) and drop the reference to the local file.
