## Findings

### 1. [critical] Email can be changed without verification, and email is the identity key for Google login and agent invitations
**Location**: src/users/users.service.ts:54-67, src/users/dto/update-profile.request.ts:11-14, src/agent/agent-member.service.ts:8-19, src/auth/auth.service.ts:168-177 (re-finds B-11 part 2, left open as "decision humaine")
**Finding**: PATCH /users/me writes `email` straight to User with no OTP, no reset of `isEmailVerified`, no session impact. Every other identity flow keys on that column: `loginWithGoogle` looks the account up by Google's verified email, and `addMember` resolves an invitation by `findUserByEmail`.
**Evidence**: (1) Pre-hijack of invitations (tenant isolation): attacker registers with his own mailbox, verifies, PATCHes email to `colleague@victim-corp.com`. When a victim workspace owner shares an assistant with that address (POST /workspaces/:ws/agents/:agent/members), `findUserByEmail` returns the attacker's account, `hasAgentAccess` is then true for the attacker, and he can read the assistant's conversations/sources and download any document of the agent's datasets via /assistants/:agentId/sources/url (signed S3 URL). (2) Account takeover of a later Google signup: the real owner of the address clicks "Sign in with Google"; `findOneWithCredentials({email})` returns the attacker's verified account whose password the attacker knows; the victim lands in an account the attacker keeps controlling. (3) Typo takeover: a user who mistypes his own new email loses the ability to reset the password (the reset mail goes to the typo address) and whoever owns that mailbox can run the reset flow and take the account. The audit entry was closed as "decision humaine requise", but this is exploitable without any precondition.
**Suggestion**: change email only through a two-step flow (pending_email + OTP sent to the new address, same HMAC mechanism as register), set `isEmailVerified=false` until confirmed, and blacklist current jtis. Until then, drop `email` from UpdateProfileRequest.

### 2. [critical] Onboarding credit bonus can be farmed indefinitely
**Location**: src/onboarding/onboarding.service.ts:60 and :95-100; prisma/schema/onboarding.prisma:14 (onDelete: Cascade on agent)
**Finding**: `grantsBonus = countByWorkspace(workspaceId) === 0` is the only guard on the +20 credits. The session row is deleted by cascade when its demo agent is deleted.
**Evidence**: DELETE /workspaces/:ws/agents/:demoAgentId (AgentController.remove, 204) removes the OnboardingSession; POST /workspaces/:ws/onboarding/start then sees count 0, creates a new demo agent/dataset and calls `grantInitial(+20, SUBSCRIPTION)` again. Loop = unlimited credits, each one written as a legitimate SUBSCRIPTION transaction (also inflates `totalGranted`). B-34 only covered workspace creation; this path is separate and still open.
**Suggestion**: record the grant on the workspace (e.g. unique CreditTransaction metadata key `onboarding_bonus` checked inside the same transaction, or a `Workspace.onboardingBonusGrantedAt` column set with an `UPDATE ... WHERE onboardingBonusGrantedAt IS NULL`), not derived from a row the user can delete.

### 3. [critical] Aborted or errored streams are never debited, even when the cost is known
**Location**: src/credit/usage-tracker.service.ts:34-55, src/agent-runtime/streaming/rag-stream-forwarder.service.ts:30-38, src/agent-runtime/streaming/sinks/persisting-result-sink.ts:44-53, transient-result-sink.ts:25-38 (follow-up of B-36)
**Finding**: B-36's fix records a log row when the client disconnects, but `recordQuery` only debits when `status === SUCCESS`. A client disconnect makes the forwarder settle with `kind: 'error'`, which both sinks map to `QueryLogStatus.ERROR`, so `creditsUsed` is written as 0 and the balance is untouched, although `outcome.costSummary` may already be present.
**Evidence**: client opens GET /assistants/:agentId/stream (or the playground), reads the first `chunk` events, closes the EventSource. `_teardownStream` destroys the upstream response, 'close' fires, `settle({kind:'error'})`, log row `creditsUsed: 0`, no decrement, `checkOrThrow` keeps passing forever. For RAG the dominant cost (embedding, rewrite, rerank and the full prompt input tokens) is spent before the first token, so a scripted client gets short answers for free at 20 req/min/IP. Same for `endedStreamErrorMessage` cases where text was streamed and then an error event arrived.
**Suggestion**: debit whenever any upstream cost is known (`costSummary` present, or fall back to the minimum unit once the stream was accepted by the engine), independent of the client-facing status; keep the status only for analytics.

### 4. [warning] Playground debits credits, contrary to the stated design (B-21 still open)
**Location**: src/agent-runtime/agent-runtime.service.ts:38-44 and :106-121, src/agent-runtime/agent-runtime.orchestrator.ts:133-135
**Finding**: `playgroundStream` passes only `forceActiveWorkflow: true`. `skipUsageTracking` stays undefined, so `_prepare` runs `checkOrThrow`, `_startOrFail(... recordFailureLog = true)` and a `logCtx` is built, so the transient sink enqueues a usage record that decrements the balance. CLAUDE.md (back and root) and the review intent say the playground is free. No test asserts either behaviour (the service spec only checks that events are emitted).
**Suggestion**: decide once, then encode it: either pass `skipUsageTracking: true` from `playgroundStream` (and keep a separate rate limit since it becomes free LLM access) or fix the docs and the front copy. Add a spec that pins the decision.

### 5. [warning] Credit check is check-then-act with a post-hoc debit: concurrent queries overshoot the balance without bound
**Location**: src/credit/usage-tracker.service.ts:62-69 and :36-46, src/agent-runtime/agent-runtime.orchestrator.ts:133-135
**Finding**: `checkOrThrow` reads `balance > 0`, the query runs for seconds to minutes, the debit happens later in a BullMQ job with `decrement` and no floor. Nothing reserves anything.
**Evidence**: with balance 1, N parallel SSE requests (N bounded only by the per-IP throttle of 20/min, per replica, in-memory) all pass the check; each later decrements its real cost (`costToCredits`, arbitrary model chosen in the workflow). Balance ends at 1 - sum(costs). The comment in recordQuery acknowledges negative balances are accepted but the intent says "never go negative unexpectedly". There is also no CHECK constraint and no DB-level invariant.
**Suggestion**: reserve atomically before the call (`UPDATE "CreditBalance" SET balance = balance - :estimate WHERE workspaceId=? AND balance >= :estimate`), then settle the delta in the processor; or at least cap concurrent streams per workspace.

### 6. [warning] Usage recording is at-least-once with no idempotency key, and the app never enables shutdown hooks
**Location**: src/agent-runtime/usage/runtime-usage-recorder.ts:18-30, usage-recording.processor.ts, src/main.ts (no `enableShutdownHooks`), src/credit/usage-tracker.service.ts:36-59
**Finding**: the enqueue is fire-and-forget (`void queue.add(...)`, errors only logged), the job has no `jobId`/request id, and `AgentQueryLog` has no unique request id, so the debit+log transaction cannot be made idempotent. main.ts never calls `app.enableShutdownHooks()` (RedisModule's `onApplicationShutdown` comment assumes it), so on SIGTERM Nest does not close the Bull workers or drain streams.
**Evidence**: (a) deploy during a stream: process killed, `settle` never reaches `recordSafely`, the query is unbilled. (b) worker killed after the Prisma transaction committed and before BullMQ acks: the stalled-job check re-queues the job and the debit is applied twice. (c) Redis blip at the moment of `add`: the usage is silently lost (Sentry only). Any of these breaks "never double-debit / never skipped".
**Suggestion**: add `requestId` (uuid generated when the stream starts) used as BullMQ `jobId` and as a unique column on AgentQueryLog, with debit and insert in the same transaction (unique violation = already applied); call `enableShutdownHooks()` and close workers on shutdown; for the enqueue-failure case fall back to a direct `recordQuery`.

### 7. [warning] Tenant filter contract with the RAG engine is implicit, undocumented and unverifiable in this repo
**Location**: src/rag-engine/pipeline.schema.ts:14-22, src/agent-runtime/agent-runtime.builder.ts:60-90, src/rag-engine/rag-execution.service.ts:60-69; rag-engine/app/blocks/retrieve_block.py, rag-engine/BLOCKS_FORMAT.md
**Finding**: isolation between customers rests entirely on the engine honouring a new `org_ids` array inside the retrieve block. `org_ids` appears nowhere in BLOCKS_FORMAT.md, and the engine copy shipped in /rag-engine only reads the top-level `org_id` (which the back still sends as `agentId`/`'onboarding'`, a value that no longer matches how documents are indexed: `indexDocument(name, datasetId, ...)` uses the dataset id). The RAG-GenRag clone that is supposed to implement it is not in the repo.
**Evidence**: against the in-repo engine the retrieve step filters on org_id=agentId and returns nothing (silent no-retrieval); against a engine that ignores both keys it would be unfiltered. Nothing in CI exercises the path (builder spec only checks the produced JSON). `deleteDocument(filename, orgId)` and `indexDocument` also depend on the same untested convention (datasetId as org_id).
**Suggestion**: document `org_ids` in BLOCKS_FORMAT.md and implement it in the bundled engine, send a single authoritative field, and add a contract test (or engine version handshake) that fails when the engine does not apply the filter.

### 8. [warning] Workflow `blocks` are trusted verbatim: collection, top_k, model and shape are client-controlled; deploy validates the wrong thing
**Location**: src/rag-engine/pipeline.schema.ts:14-35, src/workflow/dto/create-workflow.request.ts:23-24, src/deployment/deployment.service.ts:74-76, src/agent-runtime/agent-runtime.builder.ts:44-57
**Finding**: `definition` is `@IsObject()` and stored as-is. The only server-side validation is Zod at query time. `collection_name: z.string()` (BLOCKS_FORMAT/serialize.ts use a constant), `top_k: positive int` without the documented max 100, `model: z.string()` with no allow-list, and the array may be empty or lack query/answer blocks. `deploy` only inspects `nodes[].data.isPlaceholder` (UI state, also client-written) so an invalid pipeline can be deployed to PRODUCTION and only fails for end users with a 422 whose message (`Pipeline invalide : [3.model] ...`) is passed to them by `toClientSafeErrorMessage`.
**Evidence**: an editor can PATCH a workflow with `top_k: 100000` or any collection name present in Qdrant (the org filter still applies, but the collection should be server-owned) or the most expensive model; billing then follows real cost but the overshoot of finding 5 is unbounded. `blocks` and `nodes` can also diverge since the server never recomputes one from the other.
**Suggestion**: run `PipelineSchema` (with `.max(100)` on top_k, literal collection, model allow-list from /models, first=query/last=answer refinement) on workflow write and in `deploy`/`activate`; override `collection_name` server-side; hide Zod details from end users.

### 9. [warning] A retrieve block with no usable dataset is silently dropped: the agent answers ungrounded and is billed
**Location**: src/agent-runtime/agent-runtime.builder.ts:76-83, src/dataset/dataset.service.ts:146-159
**Finding**: when `resolveOrgIdsForAgent` returns [] (no dataset attached, dataset deleted, or all `datasetIds` filtered out) the retrieve block is removed and the pipeline `query -> answer` runs. Also `datasetIds: []` is overloaded to mean "all attached datasets", and only the first retrieve block's `datasetIds` are used for all retrieve blocks.
**Evidence**: product promise is answers "exclusively from the documents". Detach/delete the last dataset of a deployed agent and end users get plain LLM answers, charged to the workspace, with only a `logger.log` line. Safe from a leak standpoint, wrong from a product and billing standpoint.
**Suggestion**: fail the request (422 "no knowledge base attached") or refuse deploy/stop the agent when no dataset resolves; use an explicit marker instead of `[]` for "all datasets".

### 10. [warning] Deleting a document while it is being indexed leaves its vectors searchable
**Location**: src/document/document.service.ts:211-225, src/document/handlers/index-document.handler.ts:22-33, src/rag-engine/rag-execution.service.ts:236-272
**Finding**: `delete` calls the engine (404 swallowed as "never indexed"), then S3, then the DB row. If the BullMQ job is already inside `indexDocument` (up to 300 s of `waitForJob`), the engine delete 404s, the row disappears, and the job then finishes ingesting the file under `org_id=datasetId`. Later `updateStatus(INDEXED)` throws P2025, the job retries up to 5 times and re-ingests each time.
**Evidence**: the deleted document's chunks remain in the shared collection under a dataset that is still attached to agents, so deleted (possibly confidential) content keeps being retrieved and its name can no longer be resolved to a source. Dataset deletion has the same window (cleanup job runs 30 s after delete, `findDocumentsForCleanup` snapshot misses documents uploaded in between). Retry path is similarly not idempotent: engine identifies docs by (org, filename) so re-ingest depends on engine dedup (B-16).
**Suggestion**: soft-delete first (status DELETING), make the job re-check the row before/after ingest and delete the vectors itself when the row is gone; do not retry on P2025.

### 11. [warning] Snapshots are not immutable: `activate` + in-place `update` rewrite a deployed version; rollback destroys the draft; version numbers race
**Location**: src/workflow/workflow.service.ts:11-34, :60-82; src/workflow/workflow.repository.ts:39-54; src/deployment/deployment.service.ts:93-119; src/deployment/deployment.repository.ts:43-66
**Finding**: (a) `PATCH .../workflow/activate {id}` accepts any workflow of the agent, including the snapshot row referenced by a PRODUCTION AgentVersion; `PATCH .../workflow` then edits `findActive` in place, changing what `RagPipelineBuilder` reads via `findByVersion(prodVersion)` without a deployment. (b) `rollback` copies the old definition over the active draft (`workflowService.update`) before creating the deployment, silently dropping unsaved draft work, and the two steps are not in one transaction. (c) `nextVersion = last.version + 1` read-then-insert for both Workflow and AgentVersion: concurrent deploy/create hits the `(agentId, version)` unique index and returns a generic 500. There is no partial unique index for "one active workflow per agent" (B-24).
**Suggestion**: forbid activating/editing rows referenced by an AgentVersion (or make `definition` of snapshots write-once), do rollback as "create new active workflow from snapshot" in a transaction, take `pg_advisory_xact_lock(agentId)` (already used elsewhere in the code base) around version allocation, add `CREATE UNIQUE INDEX ... ON "Workflow"("agentId") WHERE "isActive"`.

### 12. [warning] Document retry has no status guard; create + enqueue is not atomic
**Location**: src/document/document.service.ts:94-127, :171-193
**Finding**: `retry` only checks the cool-down on `updatedAt`, not that status is FAILED (the Swagger summary says "failed document"). POST .../retry on an INDEXED or PROCESSING document resets it to UPLOADED and enqueues a second concurrent index job for the same (datasetId, filename). Separately, `ingestFile` writes S3, then the row, then `queue.add`; if Redis is down after the row exists the document stays UPLOADED forever (only a manual retry fixes it), and the storage-quota check (`getTotalSize` then insert) is not serialized, so parallel uploads exceed `MAX_DATASET_STORAGE_BYTES`.
**Suggestion**: restrict retry to FAILED (and stale UPLOADED), use `updateMany where status=...` as a compare-and-set, and add a sweeper for UPLOADED rows without a job.

### 13. [warning] Login lockout design: one shared per-email counter, non-atomic TTL, and DTO validation that never runs before the guard
**Location**: src/auth/login-attempt.service.ts:28-34, src/auth/auth.service.ts:94-111, :186-188, src/auth/token.service.ts:69-70, src/auth/auth.controller.ts:16-25
**Finding**: (a) `incr` then `expire` only when count===1: a crash/timeout between the two leaves a counter without TTL, so the account is blocked forever (`isBlocked` has no other exit). (b) Login, email OTP and reset OTP share the same key, so anyone can lock a known user out of password login, verification and password reset with 5 bad guesses every 15 min (B-42, open). (c) `isBlocked`/`recordFailure` are separate round trips, so parallel guesses all pass the check before the first failure is recorded. (d) `LocalAuthGuard` runs before the global ValidationPipe, so `LoginRequest` (IsEmail, MaxLength(72)) is dead code; a non-string `email` reaches `email.toLowerCase()` and becomes a 500 + Sentry event.
**Suggestion**: single Lua/`SET key 1 EX ttl NX; INCR` script returning the new count, key on (email, ip) or progressive delay instead of hard lock, move validation into `LocalStrategy.validate` (typeof checks).

### 14. [warning] Sessions are not revoked on password change/reset; core security switches depend on NODE_ENV === 'production'
**Location**: src/auth/auth.service.ts:36-52, :86-88, :113-115, :217-226; src/users/users.service.ts:76-89 (B-19 still open)
**Finding**: changing or resetting a password leaves every issued JWT valid until expiry (the blacklist is per-jti and only logout feeds it). Also email verification is skipped (`register` sends nothing, `verifyUser` does not require `isEmailVerified`) and the cookie drops `secure` and `sameSite=none` whenever `NODE_ENV !== 'production'`; a staging environment (NODE_ENV=staging, or a typo) is therefore an open-registration, plain-cookie deployment. Google login also never sets `isEmailVerified` for an existing unverified password account and leaves the pre-registered password in place (pre-hijack variant: the attacker's password becomes usable once the victim ever confirms the OTP the attacker triggered).
**Suggestion**: `tokenVersion` (or `passwordChangedAt` claim check) in JwtStrategy.validate; explicit flags (`REQUIRE_EMAIL_VERIFICATION`, `COOKIE_SECURE`) instead of inferring from NODE_ENV; on Google login with an unverified existing account, mark verified and null the password.

### 15. [warning] CSRF surface left open (B-04) and logout cannot clear the cookie it set
**Location**: src/auth/auth.service.ts:47-52 and :72-78 (controller), src/main.ts
**Finding**: production cookie is `SameSite=None` and Nest's default urlencoded parser is on, so cross-site form POSTs with the cookie are accepted (members POST, deployments/stop, documents/:id/retry, onboarding/start need no JSON body). GET SSE routes that spend credits and persist conversations are also cross-site triggerable. Separately `response.clearCookie('Authentication', { httpOnly: true, path: '/' })` omits `secure`/`sameSite`; for a cross-site deployment (the reason for SameSite=None) browsers ignore a Set-Cookie that defaults to Lax, so the cookie is not removed client-side (only the server-side jti blacklist saves the session).
**Evidence**: B-04 left as "decision humaine"; nothing changed since. Logout also is unauthenticated and unthrottled and uses `jwtService.decode` (no signature check), so anyone can POST /auth/logout with a forged cookie `{jti:<random>,exp:<far>}` and write one Redis key per request (TTL up to JWT_EXPIRATION).
**Suggestion**: Origin/Referer check (or double-submit token) on non-GET, pass the same cookie options to clearCookie, `jwtService.verify` before blacklisting, ThrottlerGuard on logout.

### 16. [warning] Exception filter logs the full URL including the query string, defeating the redaction done in app.module
**Location**: src/exeptions/interceptor.service.ts:26-32 (and :37 echo to client), src/app.module.ts:39-47
**Finding**: pino access logs strip the query string on purpose ("user questions on the SSE routes"), but AllExceptionsFilter logs `path: request.url` at error level for every exception, including 4xx. `?query=<question>&conversationId=...` ends up in logs (and in Sentry request data for 5xx). Every 400/401/404 is logged at `error` level.
**Suggestion**: log `request.path`/route, use `warn` for 4xx.

### 17. [warning] Missing indexes on hot paths (B-24 still open) and one concrete quadratic query

### 18. [warning] Migrations are not safe on a populated database and orphan existing vectors
**Location**: prisma/schema/migrations/20261005224546_add_dataset_model/migration.sql, 20261010120000_document_name_unique/migration.sql
**Finding**: the dataset migration drops `Document.agentId` and adds `datasetId TEXT NOT NULL` with no default and no backfill (the generated warning in the file says it fails on non-empty tables). **Suggestion**: write the data migration (one default dataset per workspace/agent, attach, re-index job) or state in the migration that it is only valid on an empty database.

### 19. [warning] Account/workspace deletion still leaves customer files and vectors behind (B-35), retention does not cover query text (B-22)

### 21. [warning] Intent/documentation drift: roles no longer exist, upstream payload is cast not validated
